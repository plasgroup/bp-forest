# 並列削除

TASK_DELETE を 1 つの DPU の全 tasklet で実行するための設計。クエリごとに「そのキーが
元々あったか」を返し、あったものは木から外す。

## 意味論

同一バッチに同じキーの削除クエリが複数あるとき、**「あった」を返すのは先頭側の 1 件だけ**
である。RESP サーバとして、バッチの先頭側のクエリが先に処理されたように見せる必要が
あるため。

## 段階

1 回の DPU 起動で 2 つの段階を通す。**返り値の位置がホストの送った順序で決まるのに対し、
木の編集はキー順に分担したい**ので、値だけを書き換えて結果配列を作る段階を先に置く。
それが終われば順序の情報は結果配列に移っているので、第二段階はクエリ列を自由に並べ替え
られる。並べ替えと分担は [parallel_batch_update.md](parallel_batch_update.md) と
[insert_handout.md](insert_handout.md) のとおりである。

2 段階分のコードは IRAM の窓に同時に載らないので overlay スロット
(`docs/dpu_iram_overlay.md`) を 2 つ使う。**クエリ列の並べ替えは第二段階のためのものだが、
後半のスロットには入りきらないので前半に置いてある。**

### tasklet の分かれ方

並べ替えに加わるのは番号が `TASK_DELETE_SORT_NR_TASKLETS` 未満の tasklet、結果配列づくりと
木の編集に加わるのは `TASK_DELETE_NR_TASKLETS` 未満の tasklet である (前者は後者以上)。

この 2 つは速度の調整用である。workspace の union の上限を決めているのは insert の
ソート枝で (実測 51,008 B)、delete 枝は既定の 16/16 でも 28,560 B である。

結果配列づくりのバリアは、並べ替えのバリア 2 つに挟まれた内側で回る。連鎖バリア
(`sync.h`) の状態は隣り合う tasklet の対ごとにあるので、外側で待っている tasklet
(番号が `TASK_DELETE_NR_TASKLETS` 以上) が触るのは対
(`TASK_DELETE_NR_TASKLETS` - 1, `TASK_DELETE_NR_TASKLETS`) から先だけで、内側とぶつからない。

## 値の表現

値は `int64_t` である。利用者が格納できるのは **63 ビット符号つきの範囲**で、その外側を
予約する。

| 値 | 意味 |
|:-|:-|
| `INT64_MIN` | tombstone |
| `INT64_MIN + 1 + t` | tasklet `t` が「消した」と返す予定 |

自分より若い印が既に入っているかどうかは `v < DELETE_CLAIM(me())` の 1 比較で判る。
tombstone は誰よりも若い側に落ちるので、この式が「既に消えたペアには手を出さない」も
兼ねる。

鍵は従来どおり `key_int64_to_uint64` で符号なしへずらす。基数ソートの桁がキーに対して
単調である必要があるためで、これは符号つき整数を基数ソートする定石である。値は順序を
`TASK_RANGE_MAX` でしか使わないので、ずらさずに比較を符号つきにする。

## 第一段階: 結果配列

クエリ列を tasklet で区間分割する。並べ替えない。

**1 パス目**は各 tasklet が自分の担当クエリのキーで木を降り、自分より若い印が入って
いなければ自分の印に書き換えて、そのスロットのアドレスを控える。**2 パス目**は控えた
アドレスを読み、まだ自分の印なら「あった」を返して tombstone に書き換える。

木の構造はこの段階では変わらないので、控えたアドレスは 2 パス目まで有効である。控え先は
ホストに返す領域の後ろに取った MRAM で、ホストは読まない。

**2 パス目が要るのは、1 パス目の時点では自分の印が後から若い tasklet に奪われるかどうかが
決まっていないためである。** 若い方が勝つ規則は、区間分割の下で「バッチの先頭側が先に
処理されたように見せる」ことと一致する。書き換えの結果が到着順に依らないので、印は最も
若い tasklet のものに収束する。

**ロック。** 1 パス目の読み書きは mutex pool で守る。ロックが要るのは 1 パス目だけである。
生き残る印は 1 つだけなので、2 パス目にあるスロットへ書き込むのは常に 1 本の tasklet で
あり、他は読むだけで、どちらの値を読んでも何もしないのが正しい動作になる。

1 パス目でも、葉ごとキャッシュへ読んだ値が既に自分より若い印であるときはロックを省く。印は
若い側へしか動かないので、一度負けた tasklet が後から勝ちに転じることはない。キャッシュ上の
値が通常の値である場合は、それを読んだ後に印が付いた可能性があるので、ロックの中で読み直す。

自分の印を書かなかったクエリはアドレスの代わりに「無し」を控える。2 パス目はそのスロットを
読むまでもなく「無かった」と答えられる。

同じ tasklet が同じキーの削除クエリを複数持つ場合は、2 パス目が担当を順に処理する間に
`INT64_MIN` へ書き戻されるので、2 件目以降は「無かった」になる。

## 第二段階: 物理削除

バケットが割り当ての最小単位なので、**並べ替えで隣り合った同じキーの並びが tasklet を
またぐことはない**。第一段階で印を付けたペアは 2 パス目で必ず tombstone になっているので、
第二段階は「キーがあれば外す」を実行するだけでよい。

### 局所木の中

下限を割りうるノードは、局所木の中に兄弟を持つ (借用と併合が局所木に閉じる) か、局所木の
根である。根は下限を免除される。

葉の調整は**その葉を離れるときにまとめて**行う。バッチがキー順なので 1 つの葉への削除は
連続し、葉あたり 1 回で済む。ペアが 1 つ消えるたびに調整すると、同じ葉を何度も兄弟と
混ぜ直すことになる。

**葉の鎖も局所木に閉じる。** 局所木を作るとき、右端の葉の `right` と左端の葉の `left` を
`NULL` に切る。切るのはどちらも自分の葉なので、隣の担当と衝突しない。おかげで葉の併合が
鎖の外へ書き込むことがない。

### 局所木どうしの連結

`JOIN_trees` と同じで、背の低い側を donor に選び、その根を解体して子を受け側の端のノードへ
移す。葉の鎖もここで繋ぐ (parallel_batch_update.md「葉の縫合」)。

**下限を割った葉は連結の場で混ぜる。** 下限を割った葉ができるのは、局所木が葉 1 枚まで
縮んだときだけである。その葉は局所木の根なので下限を免除されているが、連結で普通の葉に
なると違反になる。そこで連結は、donor が葉 1 枚でそれが下限を割っているとき、受け側の
出会う葉と混ぜる。1 枚に収まれば donor は消えるので吊るものが無くなり、収まらなければ
配り直して両方が下限を満たしてから今までどおり吊る (境目のキーだけ更新する)。どちらの
木も高さ 0 のときは、混ぜた結果が高さ 0 のままなら連結後の根なので、下限を割っていてよい。

受け側の出会う葉の親は、連結が経路として既に持っている (donor が高さ 0 なら `jp.path[0]`
が高さ 1 のノード)。親が子を失うことはないので、上へ伝播することもない。

混ぜて片方の葉が消えると、連結後の木の両端も変わる。どちらが消えたかは呼び出し側から
分からないので、連結が `leftmost_leaf` / `rightmost_leaf` を置き直す。

**混ぜてよいのは、葉の鎖を連結の中で繋いでいるからである。** 触るのは繋いだばかりの境界の
2 枚とその隣で、いずれも組み立て中の木の内側にある。

## tombstone の寿命

第二段階が毎回物理削除するので、**tombstone は DPU の起動をまたがない**。tombstone が
見えるのは第一段階の 2 パス目から第二段階までの間だけで、その間に他のタスクは走らない。
したがって木を読む側は tombstone を考えなくてよい。

## tasklet のスタック

削除の呼び出し連鎖は深い (段階の入口 → 分担の駆動 → バッチ → 葉への降下 → 葉の調整 →
上への伝播)。tasklet あたり 640 バイトしかないので、最深の経路に乗らない部分 (局所木の
構築、連結) は `noinline` にしてフレームを分けてある。MRAM の割り付けは workspace に置く。
