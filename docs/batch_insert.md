batch insertの実装
===

1.  insert queriesをキー順にソート
    *   SPMに収まる範囲ごとにbitonic sortしDRAMに書き戻す
        *   bitonic sortを選んだ理由:
            *   SPMは貴重なのでin-placeがいい
            *   16スレッドで並列に処理したい
    *   複数回の小さなsorted queriesを後からmerge
2.  ソートされたバッチを良い感じにスレッドに分配
    *   同時に、各スレッドがどのノードを変更して良いかも決める
    *   詳細は後述
3.  スレッドごとにinsertを処理
    *   変更してはいけないノードへと伝播するsplitについては、次の情報をメモっておく
        *   新しくできたノードへのポインタ
        *   新たなdelimiter key = 新しいノードが担当するキー範囲の始点
            *   splitでは右側に新しいノードを作る
        *   (どのノードへ伝播するのかはdelimiter keyから分かる)
4.  メモっておいたsplitを反映する
    *   単一スレッドでやってもいいし、兄弟ノードを並列に処理してもいい

## クエリの分配

基本的にはクエリ数が均等になるように分けるが、複数のスレッドで同じノードを変更するのは非効率なので、B+木の構造がちょうどよく切れるところに分担の境界をずらす必要がある。

### finest-grained

最もずらさ**ない**のは、葉ノードどうしの境界に合わせる実装。
境界を左側 (キーの小さくなる方向) にずらす場合:
*   まずクエリ数が均等になるように分ける
    *   各スレッドに割り振られたクエリのキーのうち最小のものを、暫定的に分担の境界とする
*   分担の境界にあたるキーでB+木を葉ノードまで探索する
    *   葉ノードに着いたら、そこにある最小のキーを、最終的な分担の境界とする
    *   道中に訪れたノードを記録しておく (Tと名付ける)

並列実行中に各スレッドが変更して良いノードの集合は次のように決まる。

*   上記の探索のうち、当該スレッドの分担範囲の始点側を決定するためにおこなったものを考え、その途中に得られた $T$ を思い出す
*   $T$ の要素と、各レベルでそれらの左側に存在するノード全てからなる集合を $T'$ とする
*   この $T'$ の要素のうち、ひとつ左側のスレッドの $T'$ に含まれていないものを $T''$ とする
*   $T''$ に含まれるノードを、変更して良い

このノード集合は、受け持つクエリが到達する葉ノードを全て含んでいる。

>   葉ノードを最小のタスクとした場合の、ADWSのinitial task mappingと同じ

### coarse-grained

上の分け方だと、葉に近いレベルでsplitを保留する必要が発生しうる。これは保留されるsplitが多くなることに繋がりかねない。そこで、rootに近いところでB+木を部分木に分け、それぞれを別のスレッドが変更して良いようにする方法も考えた。

*   まずクエリ数が均等になるように分ける
    *   各スレッドに割り振られたクエリのキーのうち最小のものを、暫定的に分担の境界とする
*   分担の暫定境界に沿って、rootの子どもたち (の下に続く部分木) を割り振る
    *   部分木の途中に暫定境界がある場合は、その部分木は境界の左側を担当するスレッドに任せる
*   スレッド0から順に、次のスレッドがひとつも子ノードを割り当てられていなかったら、次をおこなう
    *   自分が子ノードをふたつ以上割り当てられている場合:
        *   最後の子ノードを次のスレッドに譲る
    *   自分が子ノードをひとつしか割り当てられていない場合:
        *   自分と、それに続く割り当てゼロのスレッドたちに、そのノードのさらに子ノードたちを割り振る
            *   全スレッドを対象にrootの子を割り振ったのと同じ
            *   割り当てが決定するまで再帰的に降りていく

結果として、各スレッドは、連続する兄弟ノードと、その下に続く部分木を割り当てられる。その中は変更してよい。
